## 第1章 マップビュー機能の目的

### 1.1 なぜマップが必要か

Memory Synapse DBの目的は、Instagramから移行した情報を「第二の脳」として育てることである（`01_Memory_Synapse_DB_企画書v2.1.md` 1.1節）。

Locationカードには移行時点の緯度・経度が保存されており（`カード.ts` 26-30行目、`LocationSource.geo`）、人間による手書き補正座標も保存できる（`手書き情報.ts` 28-32行目、`保存用手書き情報.geo`）。これらの座標情報は現在のv1.0では一覧表示と手書き編集でしか確認できず、「どの場所にどんな記憶があるか」を直感的に振り返る手段がない。

マップビューは、これらの座標を地図上に可視化し、ピンをクリックすることでカード詳細へ到達できるようにする機能である。

### 1.2 親プロジェクトとの関係

`01_IG移行企画書v1.0.md` 1.1.2節において、GPSデータは将来的に知識基盤へ接続する情報源の一つとして明記されている。マップビューはこの長期構想と直接的に整合する。

ただし、同企画書1.1.3節の完走条件にマップ機能は含まれておらず、v1.0の完成判定とは分離する。

## 第2章 3人のAIレビューの検証と設計判断

3人のAIによるレビュー意見を、本プロジェクトの一次情報と照合し、採用・却下・保留を判断した。以下にその過程を記録する。

### 2.1 表示単位：物理カード単位か、知識単位（融合グループ）か

| 項目 | 内容 |
|---|---|
| **AI 1の意見** | Locationカードを物理単位（1ファイル＝1ピン）で表示することを推奨 |
| **AI 2の意見** | 言及なし |
| **AI 3の意見** | 言及なし |
| **一次情報との照合** | `03_表示・手書き情報.md` 5.4節（42行目）：「単独カード一枚を一知識単位、融合グループ全体を一知識単位として数える。融合グループの構成員である個別Markdownファイルは削除せず、通常表示の一覧件数に重複して数えない。」 |
| **判断** | **却下** |
| **理由** | 仕様書が定める「知識単位」の考え方はマップビューにも適用すべきである。同じ人物の居た場所が「@son_goku」と「@kakarot」で融合されている場合、物理カード単位でピンを立てると同一地点に2本のピンが立ち、融合の意味が失われる。マップ上でも融合グループごとに1ピンを基本とする。 |

### 2.2 座標データの構造とMarkdownキーの区別

| 項目 | 内容 |
|---|---|
| **AI 1の意見** | TypeScript内部の `source.geo` はプロパティ名であり、Markdownの保存キーは `geo` である |
| **AI 2の意見** | 手書き補正は `memory_synapse_note.geo` であると指摘 |
| **一次情報との照合** | `カード.ts` 22-30行目：TypeScript型 `LocationSource` に `geo: { lat: number | null; lng: number | null; alt: number | null }` が定義されている。`03_表示・手書き情報.md` 87-96行目：Markdown上の手書き座標は `memory_synapse_note.geo` として定義されている。`手書き情報.ts` 28-32行目：`保存用手書き情報.geo` は `{ lat: number | null; lng: number | null; alt: number | null }` |
| **判断** | **採用** |
| **理由** | 設計書では、移行時点座標（Markdownの `geo`、TypeScript内部では `source.geo`）と手書き補正座標（Markdownの `memory_synapse_note.geo`、TypeScript内部では `handwritten.geo`）を明確に区別して記述する。 |

### 2.3 外部通信の扱い

| 項目 | 内容 |
|---|---|
| **AI 1の意見** | v1.0の「外部通信ゼロ」と矛盾する。v1.1以降のオプション機能とすべき |
| **AI 2の意見** | タイル番号取得によるアクセス地域の推定リスク、OSM利用規約の遵守を指摘 |
| **AI 3の意見** | 言及なし |
| **一次情報との照合** | `05_ブラウザー確認・Obsidian実装・実物検証.md` 147行目：合格条件に「外部通信が発生しない」と明記。設計書 `04_確認環境・実装環境.md` 7.3節：「プラグインや外部サービスは、オーナーの確認なしに個人データを外部へ送信しない」 |
| **判断** | **採用** |
| **理由** | 地図タイル取得には外部通信が必須だが、v1.0の合格条件「外部通信が発生しない」を破ることはできない。マップビューは初期状態で通信無効とし、利用者が設定画面でリスク（IPアドレスとタイル番号からアクセス地域が推定される可能性）を理解した上で明示的に有効化する仕組みとする。Leaflet.js本体とCSSはプラグインのビルド時にバンドルし、CDN等への外部スクリプト要求を発生させない。 |

### 2.4 座標ペアの検証

| 項目 | 内容 |
|---|---|
| **AI 2の意見** | 緯度 -90〜90、経度 -180〜180 のペア検証が必要。片方不正ならペアごと破棄。(0, 0) は正常値として扱う |
| **一次情報との照合** | `手書き情報.ts` 66-69行目の `parseNum` 関数は `Number()` で数値変換し `isNaN` チェックのみ行っている。範囲検証は未実装。`カード.ts` 27-28行目の `LocationSource.geo` は `number | null` 型で、範囲制約は型定義に含まれていない |
| **判断** | **採用** |
| **理由** | 移行データには不正な座標が混入している可能性がある。マップピン生成時に範囲検証を追加することは既存の保存ロジックには影響しない（読み取り時のフィルタリングのみ）。検証ロジックの詳細は追加仕様書に定める。 |

### 2.5 UIの結合度と選択制御

| 項目 | 内容 |
|---|---|
| **AI 2の意見** | 現在の `共有UI.ts` は一覧と詳細が密結合しており、マップのような独立ビューからカード詳細を開くためには選択制御APIの分離が必要 |
| **一次情報との照合** | `共有UI.ts` 46行目：`let selectedCardId: string | null = null;` はモジュールスコープの変数であり、外部から参照・変更する手段がない。`mountUI` 関数（65-76行目）は状態、コミットコールバック、ファイルオープンコールバックを受け取るが、選択カードの変更を外部から通知する仕組みはない |
| **判断** | **採用（ただし実施時期はマップ実装開始時）** |
| **理由** | マップのピンクリックから右サイドバーのカード詳細を開く場合、現在の構造では不可能。しかしこのリファクタリングはv1.0の凍結コードに影響するため、マップ実装を開始する時点で別途承認を得て実施する。v1.0完走前には手を付けない。 |

### 2.6 XSSの防御

| 項目 | 内容 |
|---|---|
| **AI 2の意見** | ポップアップの文字列結合はXSSの脆弱性を生む。`textContent` を使用すべき |
| **一次情報との照合** | 現在の `共有UI.ts` はHTML文字列テンプレートで画面を構築している（`main.js` 440-470行目付近のテンプレートリテラル）。ただし、エスケープ関数 `r()` を通してからHTMLへ埋め込んでおり、現時点で直接的なXSS脆弱性は確認されていない |
| **判断** | **採用** |
| **理由** | マップの吹き出しはLeafletのPopup APIを使うことになり、既存の `r()` エスケープの保護外になる。新規に作るマップ関連のDOM生成では、`textContent` によるテキストノード設定を原則とする。 |

### 2.7 仮プラグインの書き込み処理について

| 項目 | 内容 |
|---|---|
| **AI 2の意見** | `Obsidian画面.ts` が「変更処理はありません」と表示しながら `processTransaction` を呼んでいるのは仕様違反 |
| **一次情報との照合** | `Obsidian画面.ts` 88行目で `processTransaction` を呼び出し、136-137行目で「作成・変更・削除処理はありません」と表示しているのは事実。しかし **ビルド済みの `06_仮プラグイン/main.js` を検索した結果、`processTransaction` `vault.process` `vault.modify` のいずれも関数名としては見つからなかった**。esbuildのminifyとtreeShakingにより、ブラウザー確認版用のダミーデータ経路では書き込み処理が呼ばれないコードパスとなっている可能性がある。ただし、ビルド済み `main.js` の末尾（472行目付近）には `Nn`（processTransactionの圧縮名と推定される関数）への呼び出しコードと `mt`（状態差分から更新を生成する関数）の定義が残っているため、**Obsidianの実Vault上で動作させた場合にはVault書き込みが実行される経路が存在する** |
| **判断** | **記録として保留。マップ設計の前提条件としない** |
| **理由** | この問題はv1.0の正式プラグイン（`08`）移行時に改めて判断すべき事項であり、マップ機能の追加設計とは独立した課題である。本設計書ではこの事実を記録にとどめ、マップ設計の前提条件には含めない。 |

## 第3章 アーキテクチャ設計

### 3.1 画面構造

マップビューはObsidianの `ItemView` を継承した独立タブとして登録する。既存のMemory Synapse DB画面（リンク一覧・カード詳細）とは別タブで開く。

現行のビルド構成（`esbuild.config.mjs`）では、`Obsidian画面.ts` をエントリポイントとして `06_仮プラグイン/main.js` へバンドルしている（20行目）。マップビューを追加する場合は、同じエントリポイントから新しい `ItemView` を登録するか、別エントリポイントを追加するかを仕様策定時に決定する。

### 3.2 データの流れ

```
Locationカード（Markdown）
  └─ カテゴリ固有YAML → geo: { lat, lng, alt }     …移行時点の座標
  └─ ## 手書き情報 → memory_synapse_note.geo         …人間の補正座標

  ↓ 読み取り（既存の scanSynapses 関数で取得済み）

LocationCard オブジェクト
  ├─ source.geo           …移行時点座標（number | null）
  └─ handwritten.geo      …手書き座標（画面用は string、保存用は number | null）

  ↓ マップデータ抽出（新規モジュール）

MapPin[]
  ├─ 座標ペア検証（範囲チェック）
  ├─ 手書き優先判定（手書き有効ならそちらを採用）
  └─ 融合グループ集約（知識単位ごとに1ピン）

  ↓ 描画

Leaflet地図上のマーカー → クリックで選択制御APIを呼び出し → カード詳細表示
```

### 3.3 5責任構造との対応

現行コードの5フォルダ構造に沿って、マップ関連のコードを配置する。

| フォルダ | マップ関連の追加内容 |
|---|---|
| `01_データ構造` | マップピン型（`MapPin`）、座標判定結果型、マップ設定型 |
| `02_操作処理` | 座標ペア検証関数、手書き優先判定関数、融合グループ集約関数 |
| `03_データ入出力` | 変更なし（既存の `scanSynapses` が返す `LocationCard` をそのまま使う） |
| `04_画面` | `マップ画面.ts`（Obsidian `ItemView` 継承）、Leafletインスタンス管理 |
| `05_共通処理` | マップ通信許可フラグの管理 |

### 3.4 外部ライブラリの管理

Leaflet.jsはnpmパッケージとしてインストールし、esbuildでプラグインの `main.js` へバンドルする。Leaflet.cssはプラグイン素材の `styles.css` へ結合するか、別ファイルとしてプラグインディレクトリに配置する。いずれの場合もCDNや外部URLへのリクエストは発生させない。

## 第4章 段階的検証フェーズ

マップ機能の実装は以下の段階で進め、各段階の完了を確認してから次へ進む。

### 第1段階：仕様の確定

追加仕様書（`99_将来拡張案/2026-07-28_マップビュー機能_追加仕様書.md`）の内容をオーナーと確認し、座標判定規則、表示単位、通信制御、XSS防御の仕様を確定する。

### 第2段階：選択制御の分離

`共有UI.ts` の `selectedCardId` 管理を外部から呼び出せる形に分離する。この変更はv1.0凍結コードへの変更となるため、別途オーナーの承認を得る。

### 第3段階：座標抽出モジュールの実装とテスト

`02_操作処理/` に座標ペア検証・手書き優先判定・融合グループ集約の関数を追加し、ユニットテストで動作を確認する。この段階ではUIは作らない。

### 第4段階：ローカル地図での動作確認

通信を無効にした状態で、ローカル画像（`ImageOverlay`）を地図の代わりに使い、ピンの配置と吹き出し表示が正しく動作することを確認する。

### 第5段階：Obsidian ItemView への組み込み

マップ画面をObsidianの独立タブとして登録し、専用テストVaultで動作を確認する。

### 第6段階：オンラインタイル接続

通信許可設定を有効にした状態で、OpenStreetMap等のタイルサーバーからの地図表示を確認する。

### 第7段階：実データでの最終検証

検証Vault上で実データ（`output_IGC` のLocationカード）を用いて、ピン数・座標・吹き出し内容・カード詳細への遷移を確認する。
