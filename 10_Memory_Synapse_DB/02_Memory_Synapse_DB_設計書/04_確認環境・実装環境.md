# Memory Synapse DB 設計書 v1.0 — 確認環境・実装環境

## 第7章 確認環境と実装環境

### 7.1 ブラウザー上の設計確認

画面と操作は、Obsidianプラグインへ固定する前に、独立した公開用検証データを使うブラウザー上の検証環境で確認する。実Vault、利用者自身の変換成果物および日常利用データを直接読み書きしない。

少なくとも、同じカテゴリ同士、異なるカテゴリ同士、融合関係への追加、融合関係同士、カテゴリ別代表、個別カードの手書き情報を反映した読み取り専用集約表示、関係を管理するカード自身の分離を確認する。

ブラウザーで使いやすく見えることだけを完成根拠にしない。確認結果を設計と仕様へ反映した後、Obsidianプラグイン、Wikiリンク、Markdown実物で再確認する。

`05_Memory_Synapse_DB_サンプル検証キット/`は、ブラウザー確認用モック、サンプルデータ、サンプルVault、検証ケース台帳、写真・動画と出典を一つの独立検証資産として保持する。ブラウザー確認用モックは、サンプルデータ、検証ケースおよびブラウザー上の状態を用いるモックであり、プラグイン実行コードから生成する成果物として扱わない。採用した画面と操作は設計・仕様へ統合し、サンプルのデータ構造またはObsidian風の仮表示を実装根拠にしない。

### 7.2 公開確認の三段階

第三者が未知のプラグインを直ちに自分の環境へ導入しなくても確認を進められるよう、公開確認を次の三段階に分ける。

1. 05のサンプルデータとブラウザー確認用モックにより、インストールせずに画面、操作および検証ケースを確認する。
2. 承認済み設計・仕様、人間が読めるTypeScript元コード、依存関係およびビルド経路を確認し、生成物が元コードから再現できることを確認する。
3. 読み取り専用仮プラグインを専用検証Vaultへ導入し、公開用検証データから用意したVault、または利用者自身が親プロジェクトでローカル変換した成果物を用いて、Obsidian実物を確認する。

前段階の合格を後段階の合格へ読み替えない。ブラウザー確認、コード監査、Obsidian実物確認は、同じ設計・仕様と検証条件を異なる境界から確認する。

第三者から得た問題報告、改善案またはコード変更案は、そのまま生成物へ取り込まない。設計変更、仕様変更、実装不具合、新機能候補または未確認へ分類し、必要な正本の承認と実装検証を経て次の読み取り専用仮プラグインへ反映する。

### 7.3 読み取り専用仮プラグイン

読み取り専用仮プラグインは、単なる件数計測器または動作しない途中成果物ではなく、その時点で承認されている画面、読取、表示、移動および非永続の操作をObsidian上で確認できる公開技術版とする。「仮」は、正式版として固定していないことと、書き込み可能な運用版ではないことを示す。

読み取り専用仮プラグインは、Vault内のSynapseと関連投稿を実際に読み、Obsidian標準機能と組み合わせて動作する。公開用検証データ、検証番号、サンプルメディアまたはブラウザー用画面をプラグイン本体へ内蔵しない。専用検証Vaultと利用者自身の変換成果物を同じ読取経路で扱い、Markdownの作成、変更、移動または削除を行わない。

読み取り専用仮プラグインは、現段階の承認範囲に対して完成を判定できる。第三者確認またはオーナー確認で新しい問題や改善案が見つかった場合は、問題を分類し、設計・仕様・実装の対応工程を経て更新する。読み取り専用仮プラグインの成立は、書き込み可能な正式プラグインの完成を意味しない。

### 7.4 正式Obsidianプラグイン

正式Obsidianプラグインは、人間が`output_IGC`の個別カードと出どころを確認し、Markdownを実体として知識を育てる最終操作入口とする。

プラグインは、融合、追加、分離、関係を管理するカードとカテゴリ別代表の選択・変更、個別カードの手書き情報の追記・編集、読み取り専用集約表示、操作前の影響確認、取消と復旧を扱う。抽出工程で欠落した事実を推測して補わず、似ているという理由だけで意味を自動確定しない。

ブラウザー上の確認、コード監査、読み取り専用仮プラグインによるObsidian実物確認を経て設計と仕様を承認した後、書き込み可能な正式プラグインをTypeScriptで実装する。正式版は、読み取り専用仮プラグインを直接書き換えて完成扱いにせず、承認済み仕様、保存処理および受入試験を別の停止点で確認する。

この判断はプラグインの実装言語と工程境界を固定し、具体的な画面配置、保存形式、処理手順、フォルダー名、ビルドコマンドまたは公開手順を先取りしない。

### 7.5 ローカルと外部AI

知識の正本は、オーナーが管理するiMac内のMarkdownと関係情報とする。プラグインや外部サービスは、オーナーの確認なしに個人データを外部へ送信しない。

外部AIの利用自体は禁止しない。利用する場合は、対象、目的、送信する情報をオーナーが確認して判断する。AIは候補提示や比較を支援できるが、意味関係を自動確定しない。

## 第8章 仕様へ渡す内容

仕様書では、少なくとも次を実装者が推測しなくてよい粒度で定める。

- 個別カードと融合関係を識別する具体的な項目と形式
- Wikiリンクの配置、更新、改名・移動時の扱い
- 関係を管理するカード、カテゴリ別代表および全構成員を表示する具体的な方法
- 読み取り専用集約表示、個別カードの通常表示および手書き編集画面
- 融合、追加、分離、関係を管理するカードとカテゴリ別代表の変更、全体解体の操作手順
- 候補提示、選択、実行前確認、完了表示、エラー表示
- 手書き情報と補正情報の保存、編集、引継ぎ
- 途中失敗、取消、復旧、再実行の単位と合否条件
- 公開用検証データの正本、ブラウザー用表現、専用検証Vault用表現の対応
- ブラウザー確認、コード監査、読み取り専用仮プラグインおよび正式プラグインの成果物境界
- 三段階の公開確認で使うケース、判定条件および次段階へ進む停止点
- 読み取り専用仮プラグインで許可する非永続操作と禁止するVault変更
- 第三者からの問題報告、改善案およびコード変更案を正本と実装へ反映する条件

現在の設計では、具体的な保存項目、画面配置、操作部品、処理アルゴリズムは確定しない。ブラウザー上の確認で設計上の意味を変える必要が生じた場合は、仕様へ進めず、本設計書へ戻ってオーナーの承認を得る。
