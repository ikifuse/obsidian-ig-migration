# Memory Synapse DB ビルド・検証方法

## 1. 適用範囲と開始条件

本書は、承認済み仕様から04の実行コードを検査し、読み取り専用技術検証版06を再生成してObsidianで確認する手順を定める。

- 05のサンプルデータとブラウザーモックは、本書の通常ビルドでは生成・変更しない。
- 08の書き込み可能な正式プラグインは、別承認があるまで生成しない。
- 仕様変更が必要だと判明した場合はコードを変更せず、仕様工程へ戻る。
- 現行コードまたはビルド設定が本書の境界に一致しない場合はビルドせず、実装不具合として対象と影響を報告する。

## 2. 初回準備

ターミナルで本フォルダーへ移動し、固定された依存関係を導入する。

```bash
cd 10_Memory_Synapse_DB/04_Memory_Synapse_DB_実行コード
npm ci
```

`package.json`と`package-lock.json`から、使用パッケージ、固定バージョンおよびライセンスを確認する。`node_modules/`は再生成可能なローカル依存物であり、Git管理しない。

## 3. ビルド前の境界検査

通常ビルドを実行する前に、`package.json`、ビルド設定および06の依存経路が05を入力・出力にしていないことを確認する。

リポジトリルートで次を実行する。

```bash
node 10_Memory_Synapse_DB/04_Memory_Synapse_DB_実行コード/scripts/check-plugin-boundary.mjs
```

さらに、04の通常ビルド設定が次を満たすことをコードで確認する。

- 出力先が`06_Memory_Synapse_DB_仮プラグイン/memory-synapse-db/`だけである。
- `05_Memory_Synapse_DB_サンプル検証キット/`、`ブラウザー画面.ts`、ブラウザー専用データ、検証ケース台帳およびサンプルメディアを参照しない。
- Vaultの作成、変更、改名、移動、削除、ゴミ箱移動または外部通信へ到達する処理を06へ含めない。
- 08を生成または上書きしない。

一項目でも不一致なら、後続の型検査、テストまたはビルドによって成果物を書き換えず、実装不具合として停止する。

## 4. 型検査

```bash
npm run check
```

TypeScriptの型と参照先が成立しているかを確認する。ファイルを生成しない検査である。

06を変更せず、同じ入口を一時領域へ束ねられることだけを監査する場合は次を使う。

```bash
npm run audit:bundle
```

この監査出力は`/private/tmp/memory-synapse-db-audit/`だけへ作成され、06を変更しない。

## 5. 自動テスト

```bash
npm test
```

承認済み仕様と確認ケースに対応するテストを実行する。少なくとも、融合、関係管理カードとカテゴリ別代表の推奨、分離、多重所属検出、項目単位の手書き優先、対象パス判定、標準タブへ渡すWikiリンク解析および非永続操作を対象にする。

テストの合格だけを、ビルド、コード監査またはObsidian実物確認の合格へ読み替えない。

## 6. 05の事前保護

通常ビルドが05を変更しないことを確認できるよう、ビルド前に05の状態を記録する。

```bash
find ../05_Memory_Synapse_DB_サンプル検証キット -type f \
  -exec shasum -a 256 {} + \
  | LC_ALL=C sort \
  > /tmp/msdb-05-before.sha256
```

この記録は内容比較用であり、05を変更しない。

## 7. 06の生成

```bash
npm run build
```

通常ビルドは、型検査を行った後、次だけを生成する。

```text
../06_Memory_Synapse_DB_仮プラグイン/
└── memory-synapse-db/
    ├── main.js
    ├── manifest.json
    └── styles.css
```

生成された06だけを直接修正しない。`main.js`に対応する人間可読なTypeScriptが04に存在しない場合は合格にしない。

ビルド後、05が変わっていないことを確認する。

```bash
find ../05_Memory_Synapse_DB_サンプル検証キット -type f \
  -exec shasum -a 256 {} + \
  | LC_ALL=C sort \
  > /tmp/msdb-05-after.sha256
diff /tmp/msdb-05-before.sha256 /tmp/msdb-05-after.sha256
```

差分がある場合は06を合格にせず、05へ書き込んだ依存経路を実装不具合として報告する。

## 8. コード監査

生成済み`main.js`だけでは合格にしない。次を対応づけて確認する。

- 承認済み仕様項目とTypeScript元コード
- TypeScript元コードと自動テスト
- 直接・間接依存関係
- `package.json`、`package-lock.json`、manifest原本、スタイルおよびビルド設定
- 型検査、自動テストおよび通常ビルドの結果
- 04の元コードと生成された`main.js`、`manifest.json`、`styles.css`
- 05のサンプルデータ、検証番号、サンプルメディアおよびブラウザー画面が06へ含まれていないこと
- Vault書き込みAPIと外部通信処理が06へ含まれていないこと

監査結果を報告し、06のObsidian実物確認へ進む前に停止する。

## 9. 06のObsidian実物確認

> [!warning] 日常利用Vaultへ入れない
> 最初は`05_Memory_Synapse_DB_サンプル検証キット/サンプルVault/`の複製を使用する。利用者自身のデータで確認する場合も、親プロジェクトでローカル変換した専用検証Vaultまたは実Vaultの複製を使用する。

1. 検証前に`Instagram_Logs/`配下全ファイルの内容照合値、ファイル数、相対パスおよび更新日時を記録する。
2. `06_Memory_Synapse_DB_仮プラグイン/memory-synapse-db/`を、検証Vaultの`.obsidian/plugins/`へフォルダーごと配置する。
3. Obsidianのコミュニティプラグイン一覧から読み込み、有効化時にエラーがないことを確認する。
4. 対象ルートを設定し、Tag、Mention、Location、融合状態、手書き情報、関連投稿および問題状態を読み取れることを確認する。
5. カードと関連投稿を押し、対応する実MarkdownがObsidian標準タブで開くことを確認する。
6. 写真、動画、本文、タグ、メンション、位置情報および末尾リンクが、投稿MarkdownとObsidian標準表示で確認できることを確認する。
7. B-01からB-19の画面、非永続操作、`元に戻す`および`初期状態へ戻す`を確認する。
8. 操作後、再読込後、プラグイン無効化後およびObsidian再起動後に、開始前の内容照合値、ファイル数、相対パスおよび更新日時と一致することを確認する。
9. 外部通信が発生せず、対象ルート設定以外の操作状態または履歴が保存されていないことを確認する。

B-20からB-30の検証番号、台帳、素材および公開条件は05側で確認する。06本体へ検証番号またはサンプル専用表示を実装しない。

利用者自身のJSON、変換成果物、画面画像またはログを、GitHubへアップロードすることを検証条件にしない。

## 10. 判定と停止点

不合格項目は、設計不備、仕様不備、実装不具合または未確認へ分類する。自動修正、上流工程の変更または08への実装を行わない。

各停止点で次を報告する。

- 変更ファイル
- 未変更範囲
- 根拠にした設計・仕様箇所
- 実行した検査と合否
- 05の変更有無
- Vaultの変更有無
- 未確定事項

06の合格は、その時点の読み取り専用承認範囲に対する公開技術版の合格であり、08の書き込み可能な正式プラグインの実装許可または完成を意味しない。
