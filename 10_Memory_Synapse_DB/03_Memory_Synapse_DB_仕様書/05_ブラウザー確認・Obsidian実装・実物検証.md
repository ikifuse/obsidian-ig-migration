# Memory Synapse DB 仕様書 v1.0 — ブラウザー確認・Obsidian実装・実物検証

## 第11章 ブラウザー確認画面

### 11.1 データ

ブラウザー確認では、実データを直接読み書きせず、次を含む検証用カードを使用する。

- Mention、Location、Tag各30枚
- Post、Reel、Story各30件の検証用投稿ログ
- 全カードと出現投稿が一致する、ハッシュタグ、メンション、場所の検証用SystemLogs
- 手書き情報があるカードとないカード
- 二つの融合済みグループ
- 同じカテゴリが一枚だけの融合、同じカテゴリが複数ある融合、三カテゴリが混在する融合
- 関係管理カードとカテゴリ別代表が同じ融合、異なる融合
- Tag、Mention、Locationそれぞれの種類別手書き入力
- 問題がある場合だけ表示する検査欄を確認するための異常サンプル

公開用検証データとブラウザー確認用モックは、`05_Memory_Synapse_DB_サンプル検証キット/`にまとめて公開する。05は04のプラグイン実行コードから生成せず、次の5要素を保持する。

`検証ケース台帳/cases.json`を検証ケース台帳とし、各検証番号について、役割、対象投稿ID、サンプルVault相対パス、本文条件、メディア条件、関連カード、期待する表示および欠損条件を一件ずつ保持する。ブラウザー確認画面は、この台帳、`サンプルデータ/`および`サンプルVault/`の内容と対応するブラウザー用表現を使用する。ブラウザー用表現を別のサンプル正本として手作業管理しない。

`サンプルVault/`は、ObsidianでフォルダーをVaultとして開ける公開用検証Vaultとする。投稿、Synapse、SystemLogs、Wikiリンク、本文、写真、動画および欠損ケースは、親プロジェクトの出力形式と本仕様の検証条件を維持する。`.obsidian/plugins/`、APIキー、利用者固有設定、絶対パスおよび個人情報を含めない。

`サンプルVault/写真・動画と出典/sources.json`には、各写真・動画について、Vault相対パス、元ページ、作者、ライセンスおよびライセンス参照先を記録する。写真・動画はサンプルVault内に一組だけ置き、ブラウザー確認画面とサンプルVaultは同じローカルファイルを参照する。表示時に外部ネットワークから素材を取得しない。

ブラウザー確認版は、画面、配置、操作および検証ケースを確認するためのUIモックとする。`05_Memory_Synapse_DB_サンプル検証キット/`直下のREADMEには、少なくとも次を明記する。

- 正式なObsidianプラグインではないこと
- 表示するカード、投稿、人物の活動、位置情報、関連付けおよび検査結果は、架空のサンプルデータであること
- 実在する名称を表示確認に使用する場合があっても、実際の利用者のInstagram履歴を示さないこと
- 実Vaultと`output_IGP`、`output_IGR`、`output_IGS`、`output_IGC`を読み書きしないこと
- ページ再読込で初期状態へ戻ること
- サンプルデータ、検証番号およびサンプルメディアを正式プラグインへ移植しないこと
- 写真と動画の出典および利用条件の参照先
- `サンプルVault/`は読み取り専用仮プラグインを隔離環境で確認するための公開用検証Vaultであること
- `サンプルVault/`の複製へ読み取り専用仮プラグインを導入する手順と、無効化・削除する手順

ブラウザー画面にも、`ブラウザー用UIモック`、`架空のサンプルデータ`、`実Vaultを読み込まない`、`正式プラグインではない`という四点を、初期表示から確認できる常設の説明として表示する。検証対象の画面を開いた後も、実データまたは正式プラグインと誤認しない表示を維持する。

Tagは、次のスポーツ用品15件と居酒屋の一般的なメニュー15件を含む。

- スポーツ用品: `#野球バット`、`#野球グローブ`、`#サッカーボール`、`#サッカースパイク`、`#テニスラケット`、`#テニスボール`、`#バスケットボール`、`#バスケットゴール`、`#ゴルフクラブ`、`#ゴルフボール`、`#ランニングシューズ`、`#ダンベル`、`#ヨガマット`、`#水泳ゴーグル`、`#自転車ヘルメット`
- 居酒屋の一般的なメニュー: `#枝豆`、`#冷やしトマト`、`#だし巻き卵`、`#鶏の唐揚げ`、`#焼き鳥`、`#つくね`、`#刺身盛り合わせ`、`#しめ鯖`、`#ほっけ開き`、`#揚げ出し豆腐`、`#フライドポテト`、`#もつ煮込み`、`#焼きおにぎり`、`#生ビール`、`#ハイボール`

検証用投稿ログ90件は、表示構造を重点的に確認する16件と、件数、検索、絞り込みおよび関連投稿数を確認する74件に分ける。各投稿ログは、本文とは別に次のブラウザー確認専用情報を持つ。

- 検証番号
- `重点検証`または`件数確認`の役割
- `写真1枚`、`空の本文`等の短い検証ラベル
- その投稿で確認する目的

検証番号とラベルは、投稿一覧の先頭と投稿詳細の本文より上に表示する。本文には検証説明を追加せず、空本文、改行、URL等の確認対象を変えない。

重点検証16件は次のように固定する。既存の投稿ログIDは変更せず、検証番号を別に付ける。

| 検証番号 | 投稿ログID末尾 | 種類 | 重点確認内容 |
|---|---|---|---|
| P-01 | `IG_0001` | Post | 写真なし、通常本文 |
| P-02 | `IG_0002` | Post | 写真1枚 |
| P-03 | `IG_0003` | Post | 写真複数枚 |
| P-04 | `IG_0004` | Post | 空の本文、写真1枚 |
| P-05 | `IG_0005` | Post | 長い本文、複数改行、URL、絵文字 |
| P-06 | `IG_0006` | Post | タグとメンションがなく、位置情報が1件ある |
| P-07 | `IG_0007` | Post | タグとメンションがそれぞれ複数、位置情報が1件あり、写真下の末尾リンクが1行に並ぶ |
| P-08 | `IG_0008` | Post | 存在しない写真パスを含む不完全データ |
| R-01 | `IGR_0001` | Reel | 正常な動画1件 |
| R-02 | `IGR_0002` | Reel | 動画、複数のタグ、メンション、位置情報、末尾リンク |
| R-03 | `IGR_0003` | Reel | 空の本文、正常な動画1件 |
| R-04 | `IGR_0004` | Reel | 存在しない動画パスを含む不完全データ |
| S-01 | `IGS_0001` | Story | 正常な写真1枚、名前付き位置情報なし |
| S-02 | `IGS_0002` | Story | 正常な動画1件 |
| S-03 | `IGS_0003` | Story | 空の本文、正常な写真または動画1件 |
| S-04 | `IGS_0004` | Story | 存在しないメディアパスを含む不完全データ |

残りは、PostのP-09からP-30、ReelのR-05からR-30、StoryのS-05からS-30を`件数確認`とする。重点確認内容と役割は、投稿一覧、投稿詳細および検証ケース一覧のすべてで同じブラウザー確認専用情報から表示し、別々に手書きして管理しない。

P-01とP-08、R-04、S-04を除く投稿ログには、種類と重点確認内容に合うローカルの写真または動画を1件以上付ける。写真複数枚のケースには2件以上を付ける。

写真付き投稿にTagがある場合は、先頭の写真の被写体と表示ラベルを、投稿が持つTagの少なくとも一つと一致させる。複数写真は、すべて同じTagまたは同じ投稿テーマとして理解できる素材で構成する。P-03は`#サッカーボール`に対応する写真3件を、サッカーボール単体、足元、試合風景の順で表示する。TagがないP-06では、Tagがあるように見せるラベルを追加せず、位置情報だけを持つ検証条件を維持する。動画は、投稿のTagがスポーツ用品か居酒屋メニューかに応じて、同じ分類の内容を使用する。

無関係な共通写真を投稿番号の順番だけで機械的に割り当てない。実データ、実Vault内の写真・動画および画面表示時の外部ネットワーク参照を使用しない。サンプル用に作成した素材または利用条件を確認できる素材だけをローカルへ置き、写真と動画ごとにローカルファイル、元ページ、作者、ライセンスおよびライセンス参照先を記録する。素材の出典記録はサンプルデータとともにブラウザー確認版へ含める。

ブラウザー確認画面には、必須検証条件、対応する検証番号、対象投稿をまとめた`検証ケース一覧`を設ける。一覧の項目から対象投稿を直接開けるようにする。必須検証条件がない、検証番号が重複する、表示ラベルと実際の本文またはメディア条件が一致しない場合は、ブラウザー確認を開始できる状態としない。

ページ再読込で初期状態へ戻せるようにする。確認中の操作はブラウザー内の検証状態だけへ反映する。

### 11.2 画面構成

画面は次の三領域で構成する。

1. 左領域（エクスプローラー）: Posts、Reels、Stories、SynapsesおよびSystemLogsのフォルダー階層とノート一覧
2. 中央領域（プレビュー・エディター）: 選択中ノート、投稿ログ本文、写真・動画プレビュー、SystemLogsツリー表示、カードグリッド
3. 右領域（Memory Synapseパネル）: 選択中Synapseカードの統合状態、手書き編集、関連投稿リスト

#### 11.2.4 画面間連動およびログ描画要件（2026-08-01承認追加）

- **SystemLogsのプレビュー表示**: `SystemLogs` ノート閲覧時、`- [x]` チェックボックス記法および出現投稿へのインデントツリー構造をObsidian標準のログ表示スタイルとしてレンダリングする。各項目リンクの選択により右パネルまたは対象投稿へ即座に移動できる。
- **投稿本文および末尾リンクのインタラクティブ連動**: 投稿ノート閲覧時、本文 caption 内の `#タグ` や `@メンション`、プロパティ項目および写真下の末尾Wikiリンク（`[[...]]`）はボタン形式でリンク化され、選択により対応するSynapseカードを右パネル（Memory Synapse）へ呼び出し・展開表示する。
- **右パネルからの逆引き連動**: 右パネルの関連投稿ボタン選択時、即座に中央領域の表示を対象の投稿ノートプレビューへ切り替え追従する。

1. カード一覧
2. 選択中の読み取り専用集約表示、受け皿および個別カード
3. 確認ポップアップまたは手書き入力欄

カード一覧では種類、カード名、単独・融合済みの状態を確認できるようにする。種類は文字だけでなく、Mention、Location、Tagを区別できる表示を付ける。

ブラウザー確認画面の左側エクスプローラー、タブ、左右サイドバーの外枠は、検証用ログとカードを選び、Obsidianでの見え方を確認するための仮表示とする。正式プラグインの独自エクスプローラーまたは独自タブとして実装しない。

デスクトップ幅のブラウザー確認画面では、中央領域と左右サイドバーの境界をドラッグして幅を変更できるようにする。左サイドバー、中央領域、右サイドバーには内容を操作できる最小幅を設け、一領域の拡大によって他の領域が画面外へ完全に失われないようにする。変更した幅はブラウザー内の確認状態にだけ保持し、ページ再読込で初期値へ戻す。

狭いブラウザー幅では、三領域を固定幅のまま横に並べない。中央領域を主表示とし、左右サイドバーは画面上の明示的な操作から開閉できる一時表示へ切り替える。左サイドバー、中央領域、右サイドバーのすべてへ到達でき、横方向にはみ出した内容を画面全体のスクロールだけに依存して探させない。この狭幅確認は05の配置・操作検証であり、v1.0の正式プラグイン対象をiPhone版Obsidianへ拡大するものではない。

中央の大きなカードは、第5.1節のカテゴリ別集約表示とし、手書き編集入口を置かない。右サイドバーは、融合単位を選択した場合は同じカテゴリ別集約表示、受け皿内の個別カードを選択した場合は同じカードの実効値、元情報、手書き情報、関連投稿および現在地を表示する。JSON文字列をそのまま利用者向け主表示にしない。

リンク一覧、検索・絞り込み、融合操作、選択中カードの現在地、読み取り専用集約表示、受け皿、種類別手書き画面、確認画面、問題検査表示は、ブラウザー確認で確定した操作として正式プラグインへ実装する。

### 11.3 必須操作

- ドラッグ＆ドロップによる融合開始
- `融合へ追加`
- 関係管理カードとカテゴリ別代表の選択
- `関係管理カードを変更`
- `代表を変更`
- 受け皿内または単独の個別カードにある`手書き`
- `このカードを分離`
- `融合をすべて解体`
- `元に戻す`
- `初期状態へ戻す`

### 11.4 確認ケース

| 番号 | 操作 | 合格条件 |
|---|---|---|
| B-01 | MentionとLocationを融合 | Mentionが関係管理カードに推奨され、MentionとLocationの代表が一枚ずつ確認され、別の関係管理カードも選択できる |
| B-02 | LocationとTagを融合 | Locationが関係管理カードに推奨され、LocationとTagを一件ずつ集約表示できる |
| B-03 | Tag同士を融合 | 受け入れる側が関係管理カードと代表の初期候補になり、代表を別のTagへ変更できる |
| B-04 | Mention同士を融合 | 受け入れる側が関係管理カードと代表の初期候補になり、人間が代表を確認するまで融合を確定しない |
| B-05 | 四枚を融合 | 全四枚が一つの受け皿に通常表示され、存在するカテゴリだけが代表一枚ずつ集約表示される |
| B-06 | 融合関係同士を融合 | 入れ子にならず全構成員が一列の受け皿になり、同カテゴリの既存代表が競合する場合は人間が選択する |
| B-07 | 読み取り専用集約表示 | Mention、Location、Tagの順に代表一枚ずつを表示し、関係管理カードを含む全個別カードを受け皿で短縮せず確認できる |
| B-08 | 種類別手書きと優先表示 | Tag、Mention、Locationで種類に合う入力欄だけが開き、保存した非空項目だけ手書きを優先し、空項目は同じ個別カードの元情報を表示し、中央と右サイドバーが同じ判定になる |
| B-09 | 通常構成員を分離 | 非代表なら代表を維持し、代表なら残る同カテゴリの枚数に応じて削除・自動選択・人間選択を行い、選んだ一枚だけが単独カードへ戻る |
| B-10 | 関係管理カードを分離 | 次の関係管理カードと必要な次の代表を選べ、残る代表、全個別カードの元情報および手書き情報を失わない |
| B-11 | 一枚だけ残す | 融合状態と空の受け皿が消える |
| B-12 | 元に戻す | 関係管理カードとカテゴリ別代表を含め、直前操作前の状態へ戻る |
| B-13 | キャンセル | 状態が一切変わらない |
| B-14 | 多重所属を試す | 実行されず、理由と対象が表示される |
| B-15 | 一覧件数 | 融合で知識単位が減り、分離または解体で増えるが、個別カード数は変わらない |
| B-16 | 検索・絞り込み | 種類、状態、手書き、名前、別名、関連投稿で対象を絞り、全件数と表示件数を区別できる |
| B-17 | 現在地 | 単独、関係管理カード、カテゴリ代表、その他の構成員の該当状態を判別できる |
| B-18 | 操作前後比較 | 融合、分離、解体、関係管理カード変更、代表変更、手書き保存で、関係管理カードとカテゴリ別代表を含む同じ比較項目を確認できる |
| B-19 | 問題検査表示 | 正常時は表示せず、異常時だけリンク、多重所属、入れ子、代表欠落・種類不一致・融合単位外参照等を種類別件数と対象ファイルで表示し、自動修復しない |
| B-20 | 検証投稿を一覧表示 | 全90件に検証番号と役割が表示され、重点検証16件と件数確認74件を一目で区別できる |
| B-21 | 検証ケース一覧から投稿を開く | 必須検証条件、検証番号、対象投稿が一致し、選択した投稿を直接開ける |
| B-22 | 写真・動画の正常ケースを開く | 表示ラベルどおりの件数と種類のローカルメディアが表示され、複数写真の順序を確認できる |
| B-23 | 本文と末尾リンクの重点ケースを開く | 空本文は空のまま、長文、改行、URL、絵文字、タグ、メンション、位置情報、末尾リンクは表示ラベルどおりに確認できる |
| B-24 | 欠損メディアの異常ケースを開く | 存在しない写真または動画を別の素材で補わず、欠損対象と検証番号を確認できる |
| B-25 | 検証用投稿の整合性を検査 | 必須条件の欠落、検証番号の重複、ラベルと実データの不一致がある場合は合格にしない |
| B-26 | READMEとブラウザー画面を初めて開く | UIモック、架空のサンプルデータ、実Vault非使用、正式プラグインではないことを、会話やコードを読まずに判別できる |
| B-27 | 写真付き投稿と素材の出典記録を確認 | Tagがある投稿では先頭写真とラベルがTagに対応し、複数写真が同じテーマを維持し、全素材の元ページ、作者、ライセンスを追跡できる |
| B-28 | 検証ケース台帳とサンプルVaultを照合 | 全90件の検証番号から対象投稿Markdown、関連Synapse、SystemLogsおよびメディアへ到達でき、重複または参照切れがない |
| B-29 | ブラウザー表示とサンプルVaultを照合 | 本文、関連情報、メディア件数・順序、欠損条件およびWikiリンクが同じ検証ケース台帳と一致する |
| B-30 | 公開用検証キットを検査 | 個人情報、絶対パス、APIキー、到達可能な実プロフィールURL、プラグイン本体および画面表示時の外部素材取得を含まない |
| B-31 | デスクトップ幅で左右境界を動かす | 左右サイドバーの幅を個別に変更でき、各領域の最小幅を下回らず、中央領域または反対側サイドバーが画面外へ完全に失われず、再読込で初期幅へ戻る |
| B-32 | 狭いブラウザー幅で三領域を確認 | 中央領域を主表示にしたまま、明示的な開閉操作から左サイドバーと右サイドバーの両方へ到達でき、閉じて中央領域へ戻れる |

各ケースは、結果だけでなく、オーナーが操作の意味と影響を迷わず理解できるかを確認する。

## 第12章 Obsidianプラグイン

### 12.1 実装条件

- TypeScriptで実装する。
- macOS / iMac M4のデスクトップ版Obsidianを最終対象とする。
- ObsidianのVault読込とリンク解決機能を使用する。Markdown変更機能は正式プラグインだけが使用する。
- Pythonサーバーを、融合・分離・手書きの必須条件にしない。
- 外部ネットワークへ自動接続しない。
- プラグイン内部だけに融合関係の正本を保存しない。
- `04_Memory_Synapse_DB_実行コード/`は、人間が読めるプラグインTypeScript、依存関係、manifest原本、スタイルおよびビルド設定を保持する。
- 04の通常ビルドは`06_Memory_Synapse_DB_仮プラグイン/memory-synapse-db/`を生成し、05または公開用検証データを生成・変更しない。
- 正式プラグインの生成先は`08_Memory_Synapse_DB_正式プラグイン/memory-synapse-db/`とする。
- 08のビルドは、正式実装が別に承認された後だけ実行できる別の生成対象とし、06を上書きしない。
- `06_Memory_Synapse_DB_仮プラグイン/`は、その時点の承認済み機能をObsidian上で確認できる読み取り専用の公開技術版として維持し、正式プラグインへ書き換えない。
- `05_Memory_Synapse_DB_サンプル検証キット/`は今後のUIテスト・モック環境として恒久的に維持する。正式プラグインが第13章の検証に合格した後に、別工程で`99_完了済み参考資料`へ退役させるのは`06_Memory_Synapse_DB_仮プラグイン/`のみとする。正式プラグインの実行は05または06へ依存しない。
- 05、06、08は、それぞれREADMEで目的、入力、書き込み有無、外部通信有無、導入・終了方法および次工程との境界を説明する。

### 12.2 読み込み

起動時に対象ルート内のMarkdownを読み、次の索引をメモリ上に作る。

- カードパスからカード種類
- 関係管理カードから全構成員とカテゴリ別代表
- 構成員から所属する関係管理カード
- カテゴリ別代表から対応する融合単位とカテゴリ
- Wikiリンクから解決先

対象ファイルの作成、変更、改名、移動、削除を検知した場合は、影響する索引を更新する。リンク切れや不正状態を検出した場合は、自動修復せず表示する。

通常時は問題検査欄を表示しない。問題を検出した場合だけ、少なくとも次を種類別件数で表示する。

- Wikiリンク切れ
- 複数所属または入れ子の疑い
- カテゴリ別代表の欠落、種類不一致または融合単位外参照
- `## Memory Synapse`または`## 手書き情報`の管理形式不正
- YAML解析失敗
- 未対応`schema_version`

問題表示には`対象ファイルを開く`を用意し、Obsidian標準のファイル表示で対象Markdownを開く。問題を検出した状態では、第10.3節に従って対象操作を書き込まない。

### 12.3 読み取り専用仮プラグイン

読み取り専用仮プラグインは、`06_Memory_Synapse_DB_仮プラグイン/memory-synapse-db/`へ、少なくとも`main.js`、`manifest.json`、`styles.css`を生成する。06直下のREADMEから、04のTypeScript元コード、ビルド手順、サンプルVault、導入手順、無効化・削除手順および既知の制限へ到達できるようにする。

06は、第11.2節のうちObsidian標準機能へ任せる外枠を除いた画面と、第11.3節の操作をObsidian上へ実装する。表示対象はVaultから読み取ったSynapseと関連投稿だけとし、次を満たす。

- リンク一覧、検索・絞り込み、選択中カード、現在地、読み取り専用集約表示、受け皿、種類別手書き画面、確認画面および問題検査表示を使用できる。
- カードを押すと対象Synapse MarkdownをObsidian標準タブで開く。
- 関連投稿を押すと対象のPost、ReelまたはStory MarkdownをObsidian標準タブで開く。
- 写真、動画、本文、タグ、メンション、位置情報および末尾リンクの表示は、投稿MarkdownとObsidian標準表示へ任せる。
- 融合、追加、関係管理カード変更、カテゴリ別代表変更、分離、解体、個別カードの手書き、取消および初期状態への復帰は、第10.6節に従う非永続操作として動作する。
- 画面上部と実行確認画面に、`読み取り専用`、`変更は保存されません`、`再読込でVaultの状態へ戻ります`を常時表示する。
- 対象ルート設定だけをプラグイン設定として保存できる。検証中のカード状態、入力した手書き情報、操作履歴およびサンプル判定を保存しない。
- Vaultの作成、変更、改名、移動、削除およびゴミ箱移動を行うAPIを、到達不能なコードを含めて06の生成物へ含めない。
- 公開用検証データ、検証番号、サンプルメディア、サンプル専用URLおよびブラウザー確認用の仮外枠を06の生成物へ含めない。

06は、05の`サンプルVault/`と利用者自身の変換成果物を判別する分岐を持たない。どちらも設定されたVault相対ルートから同じ処理で読み取る。

### 12.4 正式プラグインのMarkdown更新

Markdown更新では、管理対象見出し以外を変更しない。Frontmatter、カテゴリ固有YAML、関連投稿、未知の本文、改行を維持する。

文字コードはUTF-8（BOMなし）とする。既存ファイルの改行コードは維持する。

本節と第7.6節、第8章、第9章および第10.3節から第10.5節の書き込み処理は、08の正式プラグインだけへ実装する。

### 12.5 画面統合

- リンク一覧はObsidianワークスペース内のMemory Synapse DB専用ビューとして開く。
- 選択中カードの詳細、現在地、操作ボタン、読み取り専用集約表示と受け皿は右サイドバーのMemory Synapse DBビューへ表示する。第5.1節と第6.4節の項目単位の実効値を適用し、元のカテゴリ固有情報を削除または上書きしない。
- 融合先候補、関係管理カード候補、カテゴリ別代表候補、操作前後比較、種類別手書き入力はObsidianのモーダルまたは同等の一時画面へ表示する。
- ファイルを開く操作、通常のタブ、左側エクスプローラーはObsidian標準機能を使用する。
- 正式プラグインは左側へ独自エクスプローラーを追加せず、ブラウザー確認用のObsidian風外枠を再実装しない。

### 12.6 外部AI

v1.0では、外部AIへデータを送る機能を実装しない。将来追加する場合は、送信対象、目的、確認画面、送信しない選択肢を別仕様として承認する。

## 第13章 Obsidian実物検証

### 13.1 三段階の公開確認

公開された成果物は、次の順序で確認できる状態にする。

1. `05_Memory_Synapse_DB_サンプル検証キット/ブラウザー確認用モック/index.html`を開き、インストールせずに第11.4節のB-01からB-32を確認する。
2. `04_Memory_Synapse_DB_実行コード/`のTypeScript元コード、依存関係、manifest原本、スタイルおよびビルド設定を確認し、自分で06を再生成する。
3. 06を05の`サンプルVault/`の複製へ導入し、同じ検証ケースをObsidian上で確認する。必要に応じて、利用者自身がInstagram JSONを親プロジェクトでローカル変換した成果物でも確認する。

各段階のREADMEは、次段階へ進むために必要なファイル、コマンド、想定結果、中止条件、無効化・削除方法および個人データをGitHubへ送らない注意を記載する。

### 13.2 コード監査と再生成

第2段階は、少なくとも次をすべて満たした場合に合格とする。

- 06の機能へ到達する人間可読なTypeScript元コードが04に存在する。
- `package.json`と依存関係固定ファイルから使用パッケージとバージョンを確認できる。
- manifest、スタイルおよびビルド設定を確認できる。
- READMEに記載された一つの通常ビルドで06を再生成できる。
- 再生成した`main.js`が、04に存在しない独自処理を持たない。
- 06の依存経路に、05のサンプルデータ、検証ケース台帳、サンプルメディアまたはブラウザー画面が含まれない。
- 06の生成物に、Vaultの作成、変更、改名、移動、削除、ゴミ箱移動または外部通信へ到達する処理が含まれない。
- 生成済み`main.js`だけを変更し、対応するTypeScript元コードを変更しない変更案を合格にしない。

### 13.3 読み取り専用仮プラグインの検証

最初は05の`サンプルVault/`の複製を使用する。06を日常利用Vaultへ直接導入しない。利用者自身のデータで確認する場合も、実Vaultの複製または専用検証Vaultを使用する。

06は、次をすべて満たした場合に、その時点の承認範囲に対する公開技術版として合格とする。

- Obsidianのコミュニティプラグイン一覧から読み込んで有効化でき、読込エラーがない。
- 対象ルートからTag、Mention、Location、融合状態、関係管理カード、カテゴリ別代表、手書き情報、関連投稿および問題状態を読み取れる。
- リンク一覧、検索・絞り込み、選択中カード、現在地、読み取り専用集約表示、受け皿、種類別手書き画面、確認画面および問題検査表示が、第11章の確認済み配置と操作に対応する。
- カードと関連投稿を押すと、対応する実MarkdownをObsidian標準タブで開く。
- 投稿の写真、動画、本文、タグ、メンション、位置情報および末尾リンクを独自再構成せず、Obsidian標準表示で確認できる。
- 第11.3節の操作結果が画面セッション内へ反映され、`元に戻す`と`初期状態へ戻す`が第10.6節どおりに動く。
- 操作後、再読込後、プラグイン無効化後およびObsidian再起動後で、検証開始前に記録した`Instagram_Logs/`配下全ファイルの内容照合値、ファイル数、パスおよび更新日時が変わらない。
- 対象ルート設定以外の操作状態または操作履歴がプラグインフォルダーへ保存されない。
- 問題を検出しても自動修復せず、種類、件数および対象ファイルを表示する。
- サンプルVaultでB-01からB-19の操作を非永続で再現できる。B-20からB-32の検証番号、台帳、素材、公開条件およびブラウザー用外枠の狭幅表示は05側で照合し、06本体は検証番号、サンプル専用表示またはブラウザー用外枠を持たない。
- 外部通信が発生しない。

利用者自身の変換成果物による確認では、サンプルの件数や名称との一致を求めない。対象ルートの判定、実Markdownの表示、標準タブへの移動、問題検査およびVault非変更を同じ条件で確認する。利用者自身のJSON、変換成果物、画面画像またはログを、確認のためにGitHubへアップロードすることを必須にしない。

### 13.4 正式プラグインの受入試験

08の正式プラグインは、06の合格と、書き込み可能な正式実装に対する別承認の後だけ受入試験へ進める。最初は実Vaultの複製または専用検証Vaultを使用し、日常利用Vaultへ直接導入しない。

- 第11.4節のB-01からB-19の操作をObsidian上でも再現できる。
- MarkdownをObsidian標準画面で開き、融合関係と手書き情報を読める。
- Wikiリンクから各個別カードと関連投稿へ移動できる。
- 個別カードのフォルダーとファイルが融合前後で変わらない。
- 新しい融合専用カードが生成されない。
- 関係管理カードとカテゴリ別代表が`memory_synapse`から人間に読め、代表カードの値が融合状態へ複製されない。
- 集約表示は存在するカテゴリをMention、Location、Tagの順に代表一枚ずつ表示する。
- 種類別手書き画面は対象カテゴリに不要な入力欄を出さず、項目単位で手書き値と元情報を使い分ける。
- カテゴリ固有情報、関連投稿、Frontmatterが融合前後で一致する。
- 手書き補正によって投稿Frontmatterが変更されない。
- 融合関係同士を融合しても入れ子にならず、代表競合を人間が解決できる。
- 分離、解体、取消後も全カードと手書き情報が残る。
- リンク一覧の知識単位件数が融合で減り、分離または解体で増える。
- 選択中カードの現在地が、単独、関係管理カード、カテゴリ代表、その他の構成員の状態と一致する。
- 操作前後比較の変更ファイルと、実際に変更された管理対象見出しが一致する。
- 不正状態では問題種類、件数、対象ファイルを表示し、Markdownを自動修復しない。
- Obsidian標準エクスプローラーと標準タブを使用し、独自エクスプローラーを追加しない。
- 正式プラグインの実行経路へ、第11.1節のブラウザー確認専用情報、検証用投稿ログおよびサンプルメディアが入っていない。
- プラグイン停止中でもMarkdownから主要な関係を確認できる。
- 外部通信が発生しない。

### 13.5 Issue・変更案・不合格時

第三者またはオーナーが確認中に見つけた問題、疑問または新機能案は、Issue等で次を分けて記録する。

- 確認した段階
- 使用した公開用検証ケース、または個人情報を除いた再現条件
- 期待結果と実際の結果
- 設計変更、仕様変更、実装不具合、新機能候補または未確認の分類
- 影響する成果物

コード変更案は、生成済み`main.js`だけでなく、対応するTypeScript元コード、必要な自動試験および確認結果を含める。設計または仕様の意味が変わる場合は、コードを取り込む前に正本を更新し、オーナー承認を得る。マップビューその他の新機能案も、この分類と停止点を省略しない。

第13.2節から第13.4節の対象段階で一項目でも成立しない場合は、その段階の完成としない。仕様と実装のどちらが原因かを自動的に決めず、確認済み事実、影響および変更候補を分けて報告する。前段階で合格した成果物は、後段階の不合格だけを理由に自動的に破棄または全面再設計しない。

## 第14章 対象外

- AIによる意味上の同一性の自動確定
- 人間の確認を経ない自動融合・自動分離
- 未確定候補を長期間保存する常設作業台
- Instagram以外の情報源の取込み
- IGX
- 複数の融合関係への同時所属
- 受け皿の入れ子
- 投稿Frontmatterへの位置情報同期
- 実データを使ったブラウザー確認
- ブラウザー確認用の左側エクスプローラー、タブ、左右サイドバー外枠の正式プラグインへの移植
- 読み取り専用仮プラグインを正式プラグインへ上書きすること
