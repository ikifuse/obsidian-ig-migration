# AGENTS — Memory Synapse DB

## 適用範囲と上位条件

- 本文書は`10_Memory_Synapse_DB/`配下の作業に適用し、リポジトリ直下の`AGENTS.md`と併用する。
- `../01_IG移行企画書v1.0.md`をプロジェクト全体の最上位条件、`01_Memory_Synapse_DB_企画書v2.1.md`を本工程の直接の企画正本とする。
- 工程間の境界とプロジェクト共通原則は`../02_IG移行設計書/00_設計書目次.md`とそこに記載された設計6冊、Memory Synapse DB工程内部の構造と責任は専用設計が定める。
- Memory Synapse DBは、親プロジェクトが生成したSynapseを閲覧・編集・育成する独立した後続プロジェクトであり、その完成を親プロジェクトの完成条件へ含めない。
- 全体設計と専用設計の不一致を見つけた場合は、どちらかを自動的に優先せず、責任範囲、事実、影響を示して変更方針の承認を得る。

## 作業範囲と停止条件

- 閲覧や変更の対象は、対象工程の目次から選んだ分冊と必要なコード・成果物に限る。
- `10_Memory_Synapse_DB/`の外側に内容変更が必要な場合は、対象、理由、影響を示して追加承認を得る。親文書への参照更新だけを、親文書の内容変更へ広げない。
- Memory Synapse DB側の要求を理由に、完成済みのIGP・IGR・IGSへ仕様変更または実装変更を自動的に戻さない。親工程の変更が不可欠であることを現物で実証し、オーナーが別案件として承認するまで変更しない。
- 設計変更、仕様変更、05のサンプル・ブラウザーモック、04の実行コード、06の読み取り専用技術検証版、08の書き込み可能な正式Obsidianプラグイン、実物検証を異なる工程として判定する。人間の停止点は本書の`統合変更サイクル`に従ってまとめられるが、前工程の合格を後工程の合格へ読み替えない。
- ブラウザー確認中にオーナーが画面、操作または機能を採用して後続成果物への反映を求めた場合は、04、06または08を変更する前に`docs/browser-confirmation-workflow.md`を適用し、設計・仕様正本の反映と承認を完了する。
- `06_Memory_Synapse_DB_仮プラグイン/`は、その時点の承認済み機能を実Vault形式で確認する読み取り専用技術検証版とし、書き込み可能な正式版08と区別する。06の合格を08の実装許可または完成主張へ拡大しない。
- 停止点では、変更した対象、未変更範囲、検証結果、未確定事項を報告し、オーナーの確認を待つ。

## 統合変更サイクル

- 画面・操作・機能の相談から05、設計・仕様、04、06へ進む作業は、別々のルーティンではなく一つの変更サイクルとして管理する。
- 現在地は`07_Memory_Synapse_DB_承認・検証台帳.md`から読み、同じ変更案件では既存行を更新する。会話ごと、ボタンごと、承認発言ごとに新しい記録を作らない。
- 05の探索中は、最初に対象、維持条件、05以外を変更しないこと、候補完成時の停止点を確認する。この範囲内の反復は正式承認を毎回求めず、候補ができるまで05だけを変更する。
- Gitの途中保存を行う場合は、変更サイクル開始時に、対象ブランチ、WIPコミットおよびpushの一括許可を一度だけ明示確認する。許可後は同じサイクルの05探索に限り、区切りごとに`WIP（未承認）`として保存できる。
- WIPコミットまたはpushは正式採用を意味しない。`main`への直接push、merge、Pull Request、タグ、releaseは一括許可へ含めず、別の明示指示がある場合だけ行う。
- 通常の表示、配置、文言または操作の変更で設計変更がない場合は、05完成候補と対応する仕様差分を一組で提示し、一度の承認で05の採用と仕様承認を確定できる。
- 目的、責任、データ関係、保存主体またはObsidianとの境界が変わる場合は、05候補確認後に設計だけを更新して別に承認を待つ。設計承認前に仕様、04または06へ進まない。
- 仕様承認後、変更サイクル開始時に04実装、検査、06生成までの一括許可が明示されている場合は、04の各自動検査を人間承認へ置き換えず、すべて合格したときだけ06まで進んで停止する。不合格、範囲外変更または未確認事項があれば途中で停止する。
- 通常の読み取り専用変更でオーナーが判断する基本停止点は、`05完成候補と仕様差分`、`06実物`の二つとする。設計変更、08の書き込み、破壊的操作、IGP・IGR・IGSへの影響または解釈の分岐がある場合だけ追加停止する。

## 機能・画面の相談

- オーナーから画面、ボタン、操作、情報の見え方または機能について相談された場合は、提案前に対象機能の現役仕様、維持条件、現在の画面または実装を確認する。確認できない事項を推測で補わず、`未確認`と明示する。
- 提案は、確認した現状、維持する動作、今回だけ変える差分、影響先、確認方法を示してから行う。既存の採用事項と矛盾する案を、追加機能として提案しない。
- 現状確認後に質問へ直接答え、一般的なDB、Wiki、検索、ファイル管理等の既存例から、今回の目的と既存制約の両方に適合する案を少数だけ補足する。
- オーナーの希望、AIの提案、採用済み事項を区別する。提案を大量に列挙せず、設計、仕様または実装へ自動的に反映しない。
- 一般的な機能知識や会話全文は記録しない。オーナーが明示的に「覚えておいて」「後で検討する」と指定した本プロジェクト固有の案だけを、判断材料へ要約して残す。

## 実装環境とデータ保護

- ブラウザー確認は05の公開用検証データだけを使い、実際のVaultと`output_IGC`を書き換えない。05のサンプルデータまたは模擬Obsidian外枠を、04、06または08の依存経路へ入れない。
- 06は実Vault形式のMarkdownを読み、承認済みの画面、表示、標準タブへの移動および非永続操作を確認できるようにする。Markdownの作成、変更、移動、削除、融合状態または操作履歴の保存を実装しない。
- 書き込み可能な正式Obsidianプラグイン08は、三段階確認と必要な設計・仕様変更の承認後、別承認を受けてTypeScriptで実装する。Pythonサーバーを融合・分離・手書きの必須条件にしない。
- `node_modules/`は再生成可能なローカル開発用依存物であり、読み込み、編集、Git管理の対象にしない。
- 最終対象はmacOS / iMac M4のデスクトップ版Obsidianとする。最初の実物検証では、実Vaultの複製または専用の検証Vaultを使い、日常利用Vaultへ直接導入しない。
- v1.0では外部AIへデータを送る機能を実装せず、外部ネットワークへ自動接続しない。
