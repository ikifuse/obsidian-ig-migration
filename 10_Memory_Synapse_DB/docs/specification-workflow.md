# Memory Synapse DB 仕様ワークフロー

## 役割と開始条件

- 専用設計で確定した内容を、ブラウザー確認画面とObsidianプラグインへ推測なしに実装できる規則へ変換する。
- オーナーが対応設計を確認し、仕様工程への移行を承認していることを開始条件とする。
- 本ワークフローは進め方だけを定め、仕様本文を置き換えない。

## 読み込み

1. `../03_Memory_Synapse_DB_仕様書/00_仕様書目次.md`を読む。
2. 目次の読み分けから、今回の対象仕様分冊だけを選ぶ。
3. `../02_Memory_Synapse_DB_設計書/00_設計書目次.md`から、対応する設計分冊だけを読む。
4. コード・成果物は、比較が必要な対象範囲だけを読む。

旧Memory Synapse DB仕様書(v1.2)は09・10へ完全移管してアーカイブ済みのため、現在の仕様化の判断には使わない。

## 仕様化と比較

1. 対象設計の意味、責任境界、禁止事項、成立条件を維持する。
2. `../03_Memory_Synapse_DB_仕様書/00_仕様書目次.md` の役割分冊（01〜05）へ要件を適切に分配し、各分冊の既存本文へ自然な文章として統合・再構成する。独立した追記節を積み重ねて特定ファイルを肥大化させない。
3. 各分冊へ分配・統合した記述の見出しまたは該当段落末尾には`(YYYY-MM-DD / 07_台帳: サイクルID)`形式の最小限のカッコ表記を添え、07の対象サイクル節と紐付ける。同じサイクルで複数箇所へ統合した場合は同じサイクルIDを使う。
4. 入出力、項目名、型、初期値、保存先、処理順、判定式、画面操作を必要な範囲で確定する。
5. ブラウザー確認を根拠にする場合は、05の検証ケース台帳、サンプルVault、操作および結果を対応づけ、モック固有の表示やサンプル名称を要件へ混ぜない。
6. 05、コード監査、06、08で確認する条件を分け、前段階の合格を後段階の合格へ読み替えない。
7. 現行コード・成果物との不一致は、「維持」「微調整」「設計変更候補」「実装不具合」「未確認」に分類する。
8. 設計の矛盾、欠落、不成立を発見した場合は仕様化を停止し、設計工程へ戻す。
9. 07の対象サイクル節へ、変更前の問題、05で確かめた内容、採用理由、自然統合した仕様箇所、承認および検証結果を記録する。変更前後の仕様本文や会話全文は複製しない。
10. 04の実装者が05、07または会話を読まず、現役仕様だけで実装と合否判定ができることを確認する。不足があれば仕様承認前に補う。

## 停止点

- 仕様変更後は、変更分冊、維持した分冊、コード・成果物への影響、未確定事項を報告する。
- 設計変更がない通常の表示・操作変更では、05完成候補と対応する仕様差分を一組で提示できる。オーナーの一度の承認を、05の採用、仕様確定および変更サイクル開始時に一括許可された04実装への移行承認として扱う。
- オーナーが仕様を確認するまで、04、06または08を変更しない。05での未採用の試行、設計変更、08または変更サイクルの範囲外は、この承認に含めない。
