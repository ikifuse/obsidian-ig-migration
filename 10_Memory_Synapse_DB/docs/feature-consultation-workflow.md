# Memory Synapse DB 機能・画面相談ワークフロー

## 目的と適用範囲

- オーナーが画面、ボタン、操作、情報の見え方または機能について質問したときに、質問への直接回答と、関係する一般的な既存例の補足を両立する。
- 対象はアイデア相談であり、企画、設計、仕様または実装の変更許可にはしない。
- 見た目の装飾案を増やすことではなく、目的を達成する操作と情報の見え方を考える。

## 相談の手順

1. 相談対象と、オーナーが実現したいことを特定する。
2. 対象機能を定める現役仕様分冊を必ず読み、必要な範囲だけ対応設計、現在の画面、対象コードおよび確認ケースを照合する。
3. 次の`変更整合性ゲート`を作成し、事実を確認できない欄は推測せず`未確認`とする。
   - 現在の正式動作
   - 維持しなければならない既存動作とデータ
   - 今回だけ変える差分
   - 影響する設計、仕様、05、04、06、08および確認ケース
   - 影響しない範囲
   - 採用後の確認方法
   - 05の画面を使う相談では、各画面部分について、05での見え方、Obsidian実物で担当する標準機能またはプラグイン機能、05だけの表示、06での合格条件
4. 既存の採用事項との矛盾がないことを確認してから、オーナーの質問へ直接答える。
5. 一般的なDB、Wiki、検索、ファイル管理等の既存例から、今回の目的と維持条件の両方に適合する案だけを選ぶ。
6. 原則として一度に1〜3案を示し、推奨案がある場合は理由、既存動作との差分および注意点を添える。
7. オーナーの希望、AIの提案、採用済み事項、未確認事項を明示的に区別する。
8. 提案の採否が決まるまで、企画書、設計書、仕様書、コードまたは成果物を変更しない。
9. オーナーが明示的に「覚えておいて」「後で検討する」と指定した固有案だけを、`../../03_継続中の判断材料・引継ぎ/10_Memory_Synapse_DB_機能相談の判断材料.md`へ短く記録する。

現役仕様を特定できない、現行画面と仕様が食い違う、または維持条件が複数に解釈できる場合は、案を確定形で提案しない。不一致を`設計変更候補`、`仕様変更候補`、`実装不具合`または`未確認`へ分類し、確認に必要な現物を示す。

05のブラウザーモックについて相談する場合は、Obsidian風の外観を一括して「移植する」または「移植しない」と扱わない。左領域、中央領域、右領域、タブ、リンク、モーダル、境界変更等の意味のある画面部分ごとに、次のいずれかへ分類する。

- Obsidian標準機能により同じ役割と操作結果を実現する
- プラグインが独自に実装する
- 検証番号や説明等、05だけに置く

モックのHTML、CSSまたは仮外枠をプラグインへコピーしないことと、オーナーが採用した配置・操作・到達結果を06へ反映しないことを混同しない。Obsidian実物での担当と合格条件を確定できない画面変更は、見た目だけの完成案として提示しない。

## 提案時の必須出力

機能案を示す場合は、会話の要約ではなく、少なくとも次を同じ回答内で示す。
完走に不要な任意改善は、オーナーが求めていない限り提案しない。

| 項目 | 内容 |
|---|---|
| 確認した現状 | 根拠にした現役仕様、画面、コードまたは確認ケース |
| 維持条件 | 変更後も失ってはいけない動作、情報、保存状態 |
| 変更差分 | 今回追加または変更する部分だけ |
| 完走との関係 | 完走必須、問題解決に必要、任意改善または完了後候補のどれか。採用しない場合に現在の完成を妨げるか |
| 追加作業量 | 影響工程、変更対象、作業量の小・中・大、新しい変更サイクルまたは停止点の有無 |
| AIの技術判断 | サンプル、モック、自動試験および実物検証の十分性を現物根拠から判定した結果と、採用推奨または採用不可の結論。未確認なら承認を求めない |
| オーナー確認事項 | 目的、見た目、操作および到達結果のうち、オーナーが確認する内容。技術的な十分性を含めない |
| 画面対応 | 05の各画面部分、Obsidian標準機能、プラグイン独自機能、05だけの表示、06での合格条件の対応 |
| 影響先 | 設計、仕様、05、04、06、08、確認ケースごとの判定 |
| 非変更範囲 | 今回触らない成果物と動作 |
| 未確認事項 | 現物で確定できなかった事項 |
| 確認方法 | 採用後に合否を判定する操作と結果 |

## 記録しないもの

- 会話全文
- AIが一般知識として再提案できる機能一覧
- 今回の目的と関係しない案
- 採用されていない内容を確定事項に見せる記述

## 採用後の扱いと停止点

- 相談から05で試すことをオーナーが求めた場合は、相談時の変更整合性ゲートを`browser-confirmation-workflow.md`へ渡す。以後のサイクル開始、許可、07更新、採用、正本反映、実装および停止点は同文書だけに従う。
- 採用時には現物を再確認し、相談時のゲートまたは判断材料だけを正本・実装根拠として扱わない。
