# Memory Synapse DB ブラウザー確認結果・正本反映ワークフロー

## 目的と適用範囲

- 公開用サンプルデータとブラウザーモックで確かめた画面、配置、操作または機能を、同じ意味のまま設計・仕様、04の実行コード、06の読み取り専用技術検証版へ渡す。
- ブラウザー上で試行錯誤している間は正本反映を行わず、オーナーが採用して次工程への反映を求めた時点で本手順を適用する。
- 05の各試行に合わせて04を変更しない。採用内容を正本へ自然統合して仕様承認を得た後にだけ、04をその仕様どおりに実装する。
- 本書は工程を定める。企画、設計、仕様の本文正本または検証ケース台帳を置き換えない。

## 守る境界

- 05は、UIモック、検証ケース台帳、サンプルVaultおよびライセンス記録を保持する独立検証キットである。04のプラグイン実行コードから生成しない。
- ブラウザー確認版は、画面、配置、操作と検証条件を具体化する環境であり、Obsidianプラグインではない。
- サンプルVaultはObsidianと同じMarkdown・メディア境界を確認する公開用入力であり、プラグインへ組み込むデータではない。
- 06は実Vault形式だけを読む。05のサンプル専用表示、埋め込みデータ、模擬タブまたは模擬エクスプローラーを持ち込まない。
- 正式実装の根拠は、ブラウザー確認後に更新され、オーナーが承認した現役の設計・仕様正本とする。会話の要約、スクリーンショットまたはモックのコードだけを根拠にしない。
- IGP・IGR・IGSを変更しない。上流変更が不可欠な場合は停止し、現物根拠、対象、理由、影響を示して別承認を得る。

## 変更サイクルの現在地

画面・操作・機能の相談から06確認までを、一つの変更サイクルとして扱う。別のGit管理ルーティンまたは承認記録ルーティンを並走させない。

現在地は`../07_Memory_Synapse_DB_承認・検証台帳.md`の先頭プロパティ、現在地表および対象サイクル節で管理する。

| phase | 意味 | AIが変更できる範囲 | 次にオーナーが判断すること |
|---|---|---|---|
| `idle` | 進行中の変更案件なし | なし | 新しい相談内容 |
| `05_exploration` | 05で試行錯誤中 | 事前確認した05の対象だけ | なし |
| `05_candidate_review` | 05完成候補と仕様差分の確認中 | 指摘を受けた05と仕様差分だけ | 採用または修正 |
| `design_review` | 設計変更の確認中 | 対象設計だけ | 設計承認または修正 |
| `04_implementation` | 承認済み仕様を04へ実装中 | 対象04、検査、06生成 | 原則なし |
| `06_review` | 06実物の確認待ち | 不具合調査以外は変更しない | 承認または修正 |
| `completed` | 変更サイクル完了 | なし | 次の変更案件 |
| `blocked` | 不合格、範囲外または未確認 | 調査だけ | 追加判断 |

- オーナーはphase名を覚えたり、07を手動更新したりしない。AIが作業開始時に読み、工程境界で更新する。
- 同じ変更案件では同じサイクルIDの索引行と詳細節を更新し、会話、試行または承認発言ごとに別サイクルを作らない。
- 07は履歴台帳として大きくなってよい。変更前後、採用・不採用と理由、正本の自然統合先、承認、検証結果、未確認事項およびGit基準点を、対象サイクル節へ要約して残す。
- 通常は07全文を読まず、先頭プロパティ、現在地表および対象サイクル節だけを読む。過去の監査または正本上の`07_台帳`印を追跡するときだけ、該当する過去サイクル節を読む。
- 07へ設計・仕様の現在要件、コード全文、テスト出力全文または会話全文を複製しない。正式実装の要求入力は承認済みの現役仕様正本である。

## 承認と自動検査の分離

- 05探索中の個々の変更は正式承認ではない。対象と維持条件を確認した範囲で候補完成まで反復する。
- 通常の表示、配置、文言または操作変更で設計変更がない場合は、05完成候補と対応する仕様差分を同時に提示し、一度の承認で採用範囲と仕様を確定する。
- 仕様承認後の型検査、自動テスト、境界検査、ビルドおよび06生成は自動検査であり、一件ずつ人間承認を求めない。
- 06実物はオーナーが確認し、変更サイクルの最終承認とする。
- 設計変更、08の書き込み、破壊的操作、上流工程への影響または複数解釈がある場合は、通常の二つの判断点へ追加して停止する。

## Git途中保存の一括許可

Git操作は変更サイクル開始時に、次を一組として一度だけオーナーへ確認する。

- 専用ブランチ名
- 05探索中のWIPコミット
- 同じ専用ブランチへのpush
- 04・06へ進める条件と停止点

一括許可がない場合はGit操作を行わない。許可がある場合も、次を守る。

- WIPコミット名へ`WIP（未承認）`を付け、正式採用と区別する。
- 一つの会話や一つのボタンごとではなく、検査に合格した意味のある区切りで保存する。
- 05探索中は05と07以外が変更されていないことを保存前に確認する。
- `main`への直接push、merge、Pull Request、タグおよびreleaseは行わない。
- 不合格状態を保存する必要がある場合は、失敗内容と再開点を明記し、完成または承認済みと表現しない。

## 全体の流れ

1. 機能相談から始まる場合は、`feature-consultation-workflow.md`の変更整合性ゲートで、現状、維持条件、変更差分、影響先および確認方法を提案前に確認する。
2. 変更サイクルを07へ開始し、索引行と同じサイクルIDの詳細節を作る。05の対象、維持条件、停止点およびGit途中保存の一括許可を確認する。
3. `05_exploration`として、05のサンプルデータとブラウザーモックで候補完成まで画面・操作を反復する。
4. 候補完成時に変更整合性ゲートと現物を再照合し、採用項目を設計変更、仕様変更、実装不具合または未確認へ分類する。
5. 設計変更がなければ、05完成候補と対応する仕様差分を一組で提示し、承認を待つ。
6. 設計変更があれば必要な設計正本だけを更新して承認を待ち、承認後に仕様差分を提示する。
7. 05の試行履歴を入力にせず、承認済みの現役仕様正本だけに基づいて04の人間可読なTypeScriptとテストを変更し、自動検査する。
8. 検査がすべて合格し一括許可の範囲内なら、04から読み取り専用の06を再生成する。
9. サンプルVaultでObsidian実物確認を行い、オーナーの承認を待つ。
10. 06確認で表示・操作の変更希望が出た場合は、同じサイクルIDの`05_exploration`へ戻る。04を直接変更せず、05候補、正本への自然統合、仕様承認、04実装を再び通る。承認済み仕様との単純な不一致だけは実装不具合として04へ戻る。
11. 完了結果とGit基準点を07の同じ索引行と対象サイクル節へ記録する。08へ進む場合は、対象と停止点について別承認を得る。

前段階の合格を後段階の合格へ読み替えない。

## 1. 05での反復

1. `05_Memory_Synapse_DB_サンプル検証キット/README.md`から、モック、検証ケース台帳およびサンプルVaultの役割を確認する。
2. オーナーが配置、文言、操作または機能を試している間は、変更サイクル開始時に確認した範囲の05だけを変更する。個々の試行を正式承認として扱わない。
3. `検証ケース台帳/cases.json`を検証ケースの対応表とし、ブラウザー表示と`サンプルVault/`のMarkdown・メディアを同じケース番号で照合できる状態を保つ。
4. 各試行を設計・仕様へ逐次転記せず、採用済み事項と未採用案を混ぜない。
5. 05の変更を04、06、08の変更許可へ拡大しない。
6. 候補完成までは、AIが質問への回答と変更を継続できる範囲で進める。仕様解釈、既存動作の維持または対象範囲が分岐する場合だけ質問して停止する。
7. Git途中保存が一括許可されている場合は、05検査に合格した区切りでWIPコミットとpushを行い、07の対象サイクル節に未承認の途中保存であることとGit基準点を追記する。細かなコード差分はGitへ任せる。

## 2. 採用時点の確定

05完成候補を提示するときは、追加実装へ進む前に次を現物で確認する。

- 機能相談時に確認した現状、維持条件、変更差分、影響先、非変更範囲および確認方法
- 採用対象の画面、配置、文言および操作
- 対象となる05の元コードとその時点の差分
- 使用した検証ケース番号、入力、操作および結果
- `検証ケース台帳/cases.json`と対象のサンプルVault Markdown
- 正式版へ持ち込まないサンプル専用表示と模擬Obsidian外枠
- 未確定事項

相談時の変更整合性ゲートと採用時の現物が食い違う場合は、現物を自動的に正解としない。不一致を分類し、採用範囲を再確認するまで正本と04・06・08を変更しない。

スクリーンショットは表示状態の証拠として使用できるが、画像から分からない入力、状態変化、保存、再読込後の状態および失敗時動作は、コードと操作結果で確認する。

Gitコミットとpushは、変更サイクル開始時に対象ブランチと範囲を一括許可された場合だけ行う。Issue、Pull Request、merge、タグおよびreleaseは一括許可に含めず、オーナーがその操作を別に明示した場合だけ作成する。Git操作がない場合は、対象ファイル、検証ケースおよび内容差分を採用時点の現物とする。

## 3. 正本へ反映する工程の分類

| 分類 | 判断条件 | 扱い |
|---|---|---|
| 設計変更 | 目的、責任、データ関係、保存主体、05・04・06・08の境界、Obsidian標準機能との境界または禁止事項が変わる | `design-workflow.md`へ移り、対応する設計正本だけを更新する |
| 仕様変更 | 画面配置、表示項目、ボタン、文言、入力、操作順、処理順、判定、完了・失敗時動作、検証データ条件または確認ケースが変わる | `specification-workflow.md`へ移り、対応する仕様正本だけを更新する |
| 実装不具合 | 承認済み仕様は変わらず、04、05または06だけが一致しない | 正本を変更せず、不一致の事実、対象成果物および修正対象を示す |
| 未確認 | 複数の合理的解釈が残る、または採否が決まっていない | 正本と04・06・08を変更せず、オーナーへ確認する |

設計変更を含む場合は、設計承認後に仕様工程へ進む。設計の意味が変わらない場合だけ仕様工程から開始する。

## 4. 設計・仕様正本への統合

1. 対応する目次（`02_Memory_Synapse_DB_設計書/00_設計書目次.md` または `03_Memory_Synapse_DB_仕様書/00_仕様書目次.md`）から、採用内容の役割に対応する現役分冊（01〜05など）を適切に選んで分配する。特定のファイル1つに集約・集中させて肥大化させない。
2. 採用内容を各分冊の既存の該当章・節の本文へ自然な文章として統合・再構成し、末尾へ「〇〇承認追加」のような独立した追記節を積み重ねてファイルを伸ばさない。
3. 分配・統合した記述の見出しまたは該当段落末尾には`(YYYY-MM-DD / 07_台帳: サイクルID)`形式の最小限のカッコ表記を添え、07の対象サイクル節と紐付ける。同じサイクルで複数箇所へ統合した場合は同じサイクルIDを使う。
4. 既存の確認ケース番号体系を維持する。
5. 仕様は、実装者がモックや会話を再解釈しなくてよい粒度で、少なくとも次を定める。
   - 前提となるデータと状態
   - サンプルケース番号と実Vault形式との対応
   - 利用者の操作
   - 表示またはデータの期待結果
   - 再読込後に維持する情報と維持しない情報
   - 失敗時の結果
   - 実装してはいけない代替動作
   - 05、コード監査、06実物確認それぞれの合格条件
6. 07の対象サイクル節へ、変更前の問題、05で確かめた候補、採用内容と理由、自然統合した正本箇所、承認、検証結果、未確認事項およびGit基準点を記録する。正本の現在要件、実装指示書、コード差分全文または会話全文の代わりにはしない。

## 5. 正本確認の停止点

設計または仕様正本を更新したらコードを変更せず、次を報告する。

- 採用した項目と検証ケース
- 変更した正本と該当箇所
- 維持した正本
- 次工程へ渡す確認条件
- 06・08へ持ち込まないサンプル専用要素
- 未確定事項

- 設計変更がある場合は、設計変更後に停止し、仕様変更前にオーナーの承認を待つ。
- 設計変更がない場合は、05完成候補と更新した仕様正本を一組で提示し、一度の承認を待つ。
- 仕様承認後に04から06までの一括許可がある場合は、04開始前の追加承認を求めない。一括許可がない場合は04変更前に承認を待つ。

## 6. 承認後の04実装とコード監査

1. `implementation-workflow.md`を読み、承認済み仕様項目と確認ケースだけを対象にする。
2. 実装担当は承認済みの現役仕様正本を要求入力とし、05の試行履歴、07の履歴、会話、スクリーンショットまたはモックコードから不足要件を補完しない。仕様だけで実装できない場合は、04を変更せず仕様工程へ戻す。
3. 実装前に境界検査を実行する。

```bash
node 10_Memory_Synapse_DB/04_Memory_Synapse_DB_実行コード/scripts/check-plugin-boundary.mjs
```

4. 検査が既存不一致を報告した場合は自動修正せず、依存経路、影響および今回の承認範囲との関係を報告する。
5. 04のTypeScript、依存関係、ビルド設定、自動テストおよび生成先を人間が追跡できる状態にする。
6. 05は通常ビルドの入力にも出力にもせず、変更しない。
7. 型検査、自動テスト、再現可能なビルドおよび境界検査を実行する。
8. コード監査で、承認仕様、TypeScript、テスト、生成された06の対応を確認する。
9. 変更サイクルの一括許可があり、すべて合格して範囲外変更がない場合は06確認まで進む。一括許可がない、不合格がある、または範囲外変更が必要な場合は停止する。

## 7. 06によるObsidian実物検証

1. 04から`06_Memory_Synapse_DB_仮プラグイン/memory-synapse-db/`を再生成する。
2. 最初は05のサンプルVaultを複製して使う。必要な場合は、利用者自身がローカルで親プロジェクトにより変換したVault出力でも確認できる。
3. 06が実Vault形式のSynapseと投稿Markdownだけを読み、サンプルか実データかで処理を分岐しないことを確認する。
4. 仕様B-01からB-19の画面、表示、標準タブへの移動および非永続操作を確認する。
5. 写真、本文、メンション、タグ、位置情報および末尾リンクは投稿MarkdownとObsidian標準表示へ任せる。
6. 操作前後で対象Vaultの内容、ハッシュ、パスおよび更新日時が変わっていないことを確認する。
7. B-20からB-32の検証番号、台帳、素材、公開条件およびブラウザー用外枠の狭幅表示は05で確認し、06へサンプル専用表示またはブラウザー用外枠を実装しない。
8. 一項目でも不成立なら完成とせず、設計不備、仕様不備、実装不具合または未確認へ現物に基づいて分類する。
9. オーナーが表示・操作の変更を求めた場合は同じ変更サイクルの05探索へ戻し、06や04だけを先に直さない。

利用者自身のJSON、変換成果物、画面画像またはログをGitHubへアップロードすることを、検証の必須条件にしない。

## 8. 08へ進む停止点

06の確認後、次を報告して停止する。

- 05で確認したケース
- コード監査の対象と結果
- 06で確認した仕様項目と合否
- Vault非変更の確認結果
- 発見事項の分類
- 08で実装する候補と未確定事項

06は現在承認された読み取り専用範囲の技術検証版であり、08の完成ではない。08のコード変更と書き込み試験は、オーナーが対象、影響および停止点を別に承認した後にだけ開始する。
