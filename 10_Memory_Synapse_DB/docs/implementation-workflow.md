# Memory Synapse DB 実装・検証ワークフロー

## 役割と開始条件

- 承認済み仕様を、人間が監査できる04のTypeScript、再生成可能な06、Obsidian実物検証へ同じ意味のまま実装する。
- オーナーが対象実装と停止点を承認していることを開始条件とする。`browser-confirmation-workflow.md`の変更サイクル開始時に、仕様承認後の04実装、検査、06生成までを一括許可している場合は、その許可を本工程の開始許可として扱う。
- 05、04、コード監査、06、08および各実物検証を別の工程として扱い、前工程の合格を後工程の合格へ読み替えない。
- 仕様の意味、検証ケース、05・06・08の境界を実装便宜で変更しない。

## 共通の読み込み

1. `../03_Memory_Synapse_DB_仕様書/00_仕様書目次.md`を読む。
2. `../04_Memory_Synapse_DB_実行コード/00_実行コード目次.md`を読む。
3. 今回の操作、データおよび検証に必要な仕様分冊と、`../04_Memory_Synapse_DB_実行コード/TypeScript元コード/`内の対象責任フォルダーにある`00_このフォルダーの役割.md`だけを選ぶ。
4. 対象コード、テスト、ビルド設定および対象成果物を読む。`node_modules/`は読まない。
5. 設計との不一致判断が必要な場合だけ、`../02_Memory_Synapse_DB_設計書/00_設計書目次.md`から対応分冊を読む。

04の要求入力は、承認済みの現役仕様正本とする。05の試行履歴、07の履歴、会話、スクリーンショットまたはモックコードは実装要求として読まない。仕様上の`(YYYY-MM-DD / 07_台帳: サイクルID)`は履歴への参照印であり、実装に必要な要件を07から補う指示ではない。仕様だけでは実装判断ができない場合は、04を変更せず仕様工程へ戻す。

## 成果物の責任

| 対象 | 役割 | 生成・変更の原則 |
|---|---|---|
| 05 | サンプルデータ、サンプルVault、UIモック、素材出典を備えた独立検証キット | 05専用の生成・検査手順で管理し、04の通常ビルドから生成しない |
| 04 | 人間が読むTypeScript元コード、依存関係、テスト、プラグイン素材、ビルド設定 | 承認済み仕様から変更する実装正本 |
| 06 | 現在承認された機能を実Vault形式で確認する読み取り専用技術検証版 | 04から再生成し、生成物だけを直接修正しない |
| 08 | 書き込み可能な正式Obsidianプラグイン | 06検証後、別承認された仕様と試験だけを04から生成する |

04のTypeScript本体は`01_データ構造`、`02_操作処理`、`03_データ入出力`、`04_画面`、`05_共通処理`の5責任に分ける。`node_modules/`は再生成可能な依存物としてGit管理しない。

## 1. 05のサンプルデータとブラウザーモック

1. `../05_Memory_Synapse_DB_サンプル検証キット/README.md`を入口にする。
2. `検証ケース台帳/cases.json`を検証ケース台帳とし、各ケースからサンプルVaultの投稿Markdown、関連Synapse、SystemLogsおよびメディアへ到達できることを確認する。
3. ブラウザー表示とサンプルVaultを同じケース台帳から照合し、二つの異なるサンプル正本を手作業で維持しない。
4. 05は実際のVault、`output_IGC`および外部ネットワークを画面表示時に読み書きしない。
5. オーナーが採用した変更は`browser-confirmation-workflow.md`で分類し、必要な設計・仕様の承認前に04または06へ移植しない。

## 2. 04の実行コード

1. 承認された仕様項目と確認ケースだけを変更対象にする。
2. 実装前に境界検査を実行する。

```bash
node 10_Memory_Synapse_DB/04_Memory_Synapse_DB_実行コード/scripts/check-plugin-boundary.mjs
```

3. 06の依存経路へ、05のサンプルデータ、ブラウザー専用画面、模擬Obsidian外枠または絶対パスを入れない。
4. 06はVaultのMarkdownから必要な情報を読み、関連投稿をObsidian標準タブで開く。
5. 06の融合、分離、取消、手書き等の承認済み操作はメモリ内だけで行い、再読込でVaultの状態へ戻す。
6. 06でMarkdownの作成、変更、移動、削除、融合状態または操作履歴の保存を行わない。
7. 実装後に型検査、自動テストおよび境界検査を実行する。

## 3. コード監査と再生成

生成済み`main.js`だけでは合格にしない。少なくとも次を確認する。

- 仕様項目とTypeScriptの対応
- 変更したTypeScriptと自動テストの対応
- 直接・間接依存関係
- 固定された依存バージョンとライセンス
- 型検査、自動テストおよびビルドの実行結果
- 04のクリーンな状態から06を再生成できること
- 生成された`main.js`、`manifest.json`、`styles.css`と04の入力の対応
- 通常ビルドが05および公開用検証データを生成・変更しないこと

監査結果を報告する。変更サイクルの一括許可があり、全検査が合格し、05または範囲外のファイルへ変更がない場合は06生成と実物確認待ちまで進む。一括許可がない、不合格または範囲外変更がある場合は停止する。

## 4. 06の読み取り専用技術検証版

1. `../06_Memory_Synapse_DB_仮プラグイン/README.md`に、04の元コード、再生成方法、サンプルVault、導入、無効化、削除および既知の制限への入口を置く。
2. 06は、現在承認された一覧、検索、詳細表示、関係表示、関連投稿への移動、問題検査および非永続操作をObsidian上で確認できる範囲にする。
3. サンプル件数、検証番号または固有名称を前提にせず、サンプルVaultと利用者自身の変換成果物を同じVault入力として扱う。
4. 外部通信を行わず、APIキーを要求しない。
5. 書き込み不可であることを画面とREADMEから判別できるようにする。
6. 06の成立は、その時点の読み取り専用承認範囲に対する技術検証の合格であり、08の完成を意味しない。

## 5. Obsidian実物検証

1. macOS / iMac M4のデスクトップ版Obsidianを最終対象とする。
2. 最初は05のサンプルVaultの複製を使う。利用者自身のデータを使う場合も、親プロジェクトでローカル変換した専用検証Vaultまたは複製だけを使う。
3. 導入前に対象Vaultの内容、ハッシュ、パスおよび更新日時を記録する。
4. 仕様B-01からB-19の対象操作、表示および標準タブへの移動を確認する。
5. 写真、本文、メンション、タグ、位置情報および末尾リンクが投稿Markdownの内容どおりObsidian標準表示で確認できることを確認する。
6. 無効化または削除後もMarkdownから主要情報を確認できることを確認する。
7. 検証後に対象Vaultの内容、ハッシュ、パスおよび更新日時が変わっていないことを確認する。
8. 一項目でも成立しない場合は合格にせず、設計不備、仕様不備、実装不具合または未確認へ分類する。

利用者自身のJSON、変換成果物、画面画像またはログをGitHubへ送ることを検証条件にしない。

## 6. 08の書き込み可能な正式プラグイン

1. 06の検証結果と発見事項を正本へ反映し、必要な設計・仕様承認を完了する。
2. 08で実装する書き込み範囲、失敗時の復旧、試験対象および停止点について、オーナーの別承認を得る。
3. 承認後だけTypeScriptへ保存処理を実装し、08を別の生成先へ出力する。
4. Pythonサーバーを融合、分離または手書きの必須条件にしない。
5. プラグイン内部データだけを融合関係の正本にせず、管理対象外のMarkdownを変更しない。
6. 外部ネットワークへ自動接続せず、外部AIへデータを送る機能をv1.0へ含めない。
7. 06の読み取り専用試験を、08の書き込み・復旧・受入試験の代わりにしない。

## 停止点と報告

各段階で次を報告する。次工程で人間の承認を待つか、一括許可の範囲で自動検査へ進むかは、`browser-confirmation-workflow.md`の変更サイクルと例外条件に従う。

- 変更ファイル
- 未変更範囲
- 根拠にした設計・仕様箇所
- 対応する検証ケース
- 実行した検証と合否
- 05のサンプル専用要素が06・08へ混入していないこと
- Vault変更の有無
- 未確定事項

ブラウザーモックの完成を04の変更許可へ、04のビルド成功を06の実物合格へ、06の合格を08の変更許可またはMemory Synapse DB全体の完成へ拡大しない。

変更サイクルで04から06までが一括許可されている場合、型検査、自動テスト、境界検査およびビルドの合格報告は工程証拠であり、個別の人間承認要求にしない。06実物で停止し、オーナーの確認を待つ。
