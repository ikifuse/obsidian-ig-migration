# 恒久ルールの追加・修正基準

この文書は、プロジェクト運用ルールを「追加」「既存文の修正」「文書化しない」のどれにするか判断するときだけ使う。企画・設計・仕様の内容やコマンド権限は決めない。

## 判断手順

1. 同じ誤り・誤解・修正指摘が複数回あり、将来も必要なプロジェクト固有ルールか確認する。
2. 同じ責任を持つ規則の正本を一つ特定する。AGENTS.mdまたは対応workflowに重複があれば、新しい記述を増やさず、正本以外の重複を同じ変更で削除する。
3. 原因が既存文の曖昧さまたは矛盾なら、新規追加せず、正本の既存文を一つの意味に置き換える。矛盾する二つの方針を併記したまま例外でつながない。
4. コード、テスト、lint、hook、自動化で防げるなら機械的対策を優先し、人間の判断境界だけを文書に残す。
5. 一時的な進捗・引継ぎ・未確認事項は恒久ルールにしない。例やスクリプトを伴う必須の反復作業は、共通規則をAGENTS.mdまたはworkflow、機械検査を`tools/`へ置き、使用するAIに対応したSkillは正本を実行する入口として必要性、起動条件および固有の役割を確認してから追加する。Skillだけを共通規則の正本にしない。
6. 変更対象、理由、影響を示し、オーナー承認後に反映する。
7. 既存規則の移動、統合、置き換えまたは退役では、影響する承認済み規則を一項目ずつ、現行の置き場所、維持した意味、実行方法または承認済みの退役理由へ対応付ける。形式検査や変更範囲検査だけで移行完了とせず、対応先のない項目が残る間は完了と報告しない。
8. リポジトリ共通規則または読み込み経路を変更する場合は、編集前にファイルシステム上の全`AGENTS.override.md`と`AGENTS.md`を列挙し、現役、限定的に保護する完了済み資料、完全な退役資料へ分ける。各現役階層への影響を確認し、整合だけを理由に完了済み・退役資料を書き換えない。

## 記述条件

- 適用対象、対象外、条件、例外、承認範囲を、意味が変わらない最小限の文で記す。
- 同じ規則をAGENTS.md、workflow、SkillまたはREADMEへ全文複製せず、正本以外には参照先と、その文書固有の差分だけを置く。
- 確認済み事実、仮定、提案を区別する。
- 要約や翻訳だけを変更根拠にせず、使用する製品の現在の公式資料を直接確認し、承認済み文書およびGit履歴と照合する。
- 根拠を確定できない場合は変更せず、未確認事項として報告する。
