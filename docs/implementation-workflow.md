# 実装・成果物検証ワークフロー

## この工程の役割

- 承認済み仕様を基準に、対象コードへ必要な最小差分を実装し、対象成果物が仕様どおりかを現物で検証する。
- この文書は実装・検証の進め方と停止条件だけを定め、企画・設計・仕様の内容または個別コードの実装内容を代わりに定義しない。
- コードの存在、実行成功または件数一致の一つだけで完成としない。

## 開始条件と対象

- オーナーが対象仕様、変更対象、操作および停止点を確認し、実装工程への移行を承認していることを開始条件とする。
- 対象ディレクトリの `00_コード構成.md`、目次から選んだ対象仕様書、対象コードおよび対象成果物だけを読む。
- 設計との不一致判断が必要な場合だけ、対応する現役設計分冊を追加で読む。
- 実装許可を、仕様変更、別工程、別ファイルまたは成果物再生成の許可へ拡大しない。

## 変更前の確認

1. Git差分と対象ファイルの現状を確認し、既存のオーナー変更と今回の変更を分ける。
2. 仕様、コードおよび成果物の現在の対応を確認する。
3. 不一致は「維持」「微調整」「設計変更候補」「実装不具合」「未確認」に分類する。
4. 今回維持する動作、変更する差分、影響先、検証方法および停止点を示す。
5. 複数の合理的な実装結果があり成果物が変わる場合は、推測で選ばず停止する。

## 実装

- 承認された対象コードだけを変更する。
- 期待に近い既存成果を維持し、全面再実装、リファクタリング、コード整理、将来拡張だけを理由に変更しない。
- 企画、設計または仕様の不足を、コード側の推測で補わない。仕様だけでは実装判断できない場合はコードを変更せず仕様工程へ戻す。
- IGP・IGR・IGSは実用上完成済みとして凍結し、親 `AGENTS.md` の例外条件を満たさない限り変更しない。
- IGCは `09_IGC統合/AGENTS.md`、Memory Synapse DBは `10_Memory_Synapse_DB/AGENTS.md` と各専用ワークフローを併用し、子工程の許可を上流や別プロジェクトへ広げない。

## 成果物生成と検証

- コード変更と成果物再生成を別の操作として扱い、それぞれ承認範囲を確認する。
- 実データまたは大量データを扱う前に、対象、操作および影響を示して承認を得る。
- 既存成果物へ直接上書きできる工程では、仕様が定める隔離出力、ドライラン、バックアップまたは復旧手順を先に使用する。個別工程に定めがない場合は実出力を変更せず停止する。
- 対象工程の仕様と `00_コード構成.md` に記載された検査を実行し、少なくとも構文・依存関係、入力、出力、件数、内容、リンク、エラーおよび対象外の無変更を必要な範囲で確認する。
- 最終対象環境であるmacOS / iMac M4で、パス、権限、実行方法および成果物の実物を確認する。
- 自動試験だけで見た目、操作または実物結果を判定せず、実物確認だけでコードと成果物の技術的な十分性を判定しない。

## 停止条件

次の場合は、コードまたは成果物を追加変更せず停止する。

- 承認済み仕様だけでは実装結果を一意に決められない。
- 対象外のファイル、入力または成果物への変更が必要になった。
- 上流工程、完成済み工程または別プロジェクトへの変更が必要になった。
- 検査に不合格がある、または未確認事項が残る。
- 実出力の置換、削除、移動その他の破壊的操作に別承認が必要である。

## 完了条件と報告

- 対象仕様と変更コードの対応を確認する。
- 生成した成果物が対象仕様と一致し、対象外が変わっていないことを確認する。
- 変更ファイル、未変更範囲、根拠にした仕様、実行した検証と合否、成果物変更の有無、未確定事項を報告する。
- 技術的な十分性はAIが現物根拠から判定し、未確認の状態でオーナーへ採用承認を求めない。
- オーナーへ確認する内容は、目的、見た目、操作および到達結果が希望どおりかに限定する。
- 完了報告後は、次工程、コミットまたはpushへ自動的に進まず、承認された停止点で止まる。
